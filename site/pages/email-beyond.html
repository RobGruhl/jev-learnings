Around the sorter

The sorter decides what one message deserves. Most of the gains, though, came from around it: stopping noise before it arrives, letting Jev drive the unsubscribe pages, remembering what's already done, and writing the owner's rulings down so nobody has to re-decide them. This page covers those layers, then who ended up doing what.

Cut it at the source

Noise was concentrated. Over the three labeled months, 50 senders sent nothing but noise (at least three messages each), 19% of all mail, and the top 30 senders made up 63% of the noise. The cheapest message to sort is the one that never arrives, so the layers run cheapest first:

Code L1 · Unsubscribe

Senders that only ever sent noise. The owner approves the list.

once · per sender

Code L2 · Filters

Label and archive, never delete, for mixed senders' noisy patterns. One sender sent dozens of nudges and one invitation that mattered, so it gets a pattern filter, not a block.

once · per pattern

Jev L3 · The sorter

Files the obvious noise that's left.

every message · cents

LLM L4 · Claude reads

Everything else, in a session. The owner's notes feed new proposals back into L1–L3.

per session

Unsubscribing turned out to be almost entirely automatable without a browser. Of the 50 noise-only senders, 45 supported the standard one-click unsubscribe header (RFC 8058): one HTTPS POST, no page, no mail sent. 43 of those 45 were signed by the sender's own domain. None needed an unsubscribe-by-email or a landing page.

The edge cases were standards, not judgment. A few servers answered the POST with a redirect that turned it into a GET, so those count as unconfirmed. One newsletter platform's header pointed at a custom domain that rejected the POST, while the link in the body worked. One site behind bot protection passed only in a visible browser.

Jev as the step chooser in a browser

Mixed senders need preference pages, and those come in endless wordings. That's what a decision model is good at. The loop keeps the decision model in a narrow job:

The real pages were mostly easy; keywords handled them. Jev earned its place on variety: a confirmation without the usual words, future tense ("you will be unsubscribed once you confirm"), which checked box to keep (security notices), a bare "Yes", pause versus unsubscribe, and opt-down radio buttons. It took about 0.6 s per page.

In a live run on six new senders, four were confirmed on the page with Jev choosing the steps. The other two escalated correctly. One form needed the address typed: Jev clicked Unsubscribe on the empty form, read "not recognized" and stopped, and Claude typed it. The other sat behind a bot check that never passed, so it went to the owner. The one real failure was a settings page whose switches were all labeled only "Toggle setting". The chooser flipped them back and forth until the step limit, which is risky because a flip can resubscribe. Claude checked afterwards that every switch was off. The fixes are code: attach nearby label text to unnamed controls, and never click the same control twice.

Make "done" stick

An assistant that resurfaces things you already handled isn't calm. So each action becomes a record, and later mail is matched against open records. Thread matching alone isn't enough: 57% of same-matter follow-ups arrived in a different thread. On 628 labeled pairs of an open item and a later message:

MethodRecallPrecision
Same thread only43%88%
Jev "same matter?" at 0.5, local 4B (AUC 0.955)85%68%
Jev "same matter?" at 0.5, hosted (AUC 0.980)93%77%

At that precision a match shouldn't hide anything on its own. Jev proposes the link and Claude confirms it in the session, so a new obligation can't be buried under an old one. A second question ("does this mail show the item is done?") reached 0.933 hosted.

Silence isn't the state of the world. The audit surfaced a "last chance to return leased equipment" notice that the owner had in fact already handled. The mail never said so, so a mail-only assistant would have kept raising it. Obligations can't be inferred from mail alone: the assistant needs its own record and the owner's "done" written back to it. Code now refuses an open record without a next step and a link, and links come from the raw message, never from a model's retyping.

Jev finds it, code reads it

A subscription audit put the money Choice from part 2 over about 1,300 subscription-flavored messages from two mailboxes, in about two minutes for roughly $0.10. It separated real billing (receipt, upcoming charge, trial conversion, failed payment, price change, bill due) from renewal-themed marketing well enough to review by sender. Then code took over: one store's receipts list the account, item, period, renewal date and price in fixed fields, and a 20-line parser read every one of them.

The first register still overstated what was live, in two ways. The question had no "cancelled or expiring" option, so cancellation mail landed in the nearest wrong class. And a register built from receipts alone misses cancellations: it has to take the latest state of each subscription across receipts, cancellations and expiry notices. (One app store sends no cancellation email at all, only an "expiring" notice about two weeks before the term ends.) Same lesson as the deadline Choice: name the near misses, including the one you forgot.

Rulings are the cheapest accuracy

A third of the labels were low-confidence, and the disagreements clustered on a few recurring patterns. The owner ruled on each once:

PatternLabelers splitThe owner's ruling
New sign-in alertsnow / brief / fileFile
Failing builds on the owner's own codesoon / file / briefOne standing "fix recurring errors" action per project: the first each month is soon, repeats are filed
Appointment remindersbrief / nowFile; the original booking goes on an assistant calendar instead
Utility billsfile / soonSurface only as an anomaly

Those four rulings changed the action load by about a quarter (293 items to 244). They're stored as a reversible overlay on the labels, so the sorter can be retrained either way. Every session surfaces a few new gray zones, and they go on the page as questions, not guesses. Records keep the owner's own words, and code writes them; a model never regenerates them.

Who ended up doing what

Code

Everything exact

Byte-exact harvest, sender facts from headers, the money ledger, the sorter itself, link extraction, receipt parsing, one-click unsubscribes, the record store and its rules, and the gate that keeps private mail off unapproved backends.

Jev

Bounded reads of every message

Concept answers as sorter features, matching new mail to open records, sorting billing from marketing, and choosing the next step on an unsubscribe page. Hosted, for about $0.07 per thousand requests.

LLM

Reading and writing

Claude reads every escalated message, writes the session page with next steps and links, groups by area, confirms record matches, and labels blind. It also proposes questions, phrasings and rules.

Human

Rulings and approvals

The owner rules on gray zones, approves every unsubscribe and filter, writes "done", and sets the threshold by deciding how many misses they'll accept.

What carries over

  1. Set the threshold by what a miss costs, count misses exactly, and report the filter rate at that miss count.
  2. Ask contrastive Choices that name the near misses, and grade each question against its own concept before using it.
  3. Combine answers with a learned model, pick thresholds out of fold, and validate on a new window. Watch the filter rate per window, because it drifts even when the threshold holds.
  4. When misses remain, add facts before questions. Known people, open records and standing rulings are cheap, exact and don't overfit.
  5. Cut volume at the source first. Senders that only ever sent noise accounted for nearly a fifth of all mail, and removing them cost one list review.
  6. Mail isn't the world. Keep your own records, with the owner's "done" written back.
